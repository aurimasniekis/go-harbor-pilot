# Decisions

Each entry gives the decision, its rationale, and its status. When a later entry supersedes an earlier one, it references that entry by number.

## D-001: Subscription execution uses native CLI bridges and API keys only (owner decision, 2026-11-05)

**Decision**

- Claude subscriptions run through the vendor `claude` binary.
  - Each account authenticates with a long-lived token created by `claude setup-token`, passed as `CLAUDE_CODE_OAUTH_TOKEN`.
  - Each account has its own isolated `CLAUDE_CONFIG_DIR`.
- ChatGPT/Codex subscriptions run through the vendor `codex` binary, with a separate `CODEX_HOME` per account.
- Harbor Pilot does not replay subscription OAuth tokens against vendor HTTP endpoints, and does not impersonate vendor client headers.

**Quota monitoring is separate**

- Observing subscription quota does not execute requests. Quota Harbor's monitoring adapters stay available as "unofficial, opt-in".
- Each such account must set `acknowledge_terms_risk: true`.

**Rationale**

- Running the vendor binary uses the mechanism the vendor ships for that subscription.
- Replaying tokens or impersonating headers carries terms-of-service and account-suspension risk.
- The bridge runs wherever Harbor Pilot runs. For a self-hosted deployment, that host must hold the CLI binary and the per-account logins.

## D-002: License and code hygiene (owner decision)

- Both repositories are licensed under Apache-2.0.
- Code, including comments and identifiers, never names reference projects. Reference projects are named only in `docs/` and in named integration features (Pulse relay, Porch-compatible OIDC, Quota Harbor importer, SpaceMan example).
- Magpie (MIT) is an "isolated lab". Harbor Pilot rewrites the designs it observed there from scratch, and copies none of its code or fixtures. All protocol fixtures are synthetic and written from public API documentation.
- Quota Harbor has no license file. It is the owner's own code, and the owner approved copying and evolving it.

## D-003: Commits

The owner authorized commits at logical points in both repos. Commit messages follow Conventional Commits. Nothing is ever pushed by the agent.

## D-010: One binary, one SQLite instance

Harbor Pilot keeps Quota Harbor's foundations: a single binary that serves the API, the gateway and the embedded UI, backed by modernc SQLite in WAL mode with a writer/reader split.

- Multi-writer HA is explicitly unsupported (see ARCHITECTURE §1).

## D-011: Control-plane API defined in Go types

- **Framework:** huma v2 mounted on chi (`humachi`). OpenAPI 3.1 is generated from Go types.
- **Spec in the repo:** the generated `api/openapi.yaml` is committed. A test fails when the committed file differs from the generated one.
- **Clients:** the UI imports types generated by `openapi-typescript`. The Terraform provider uses an `oapi-codegen` client generated from a vendored copy of the spec.
- **Data-plane endpoints** (the streaming protocol handlers) are plain chi handlers, documented in `docs/contracts/gateway.md`.
- **Why it deviates from Quota Harbor:** Quota Harbor hand-wrote its YAML spec and left the generated TS types unused. The brief requires a generated API that is validated against the code.

## D-012: Database is the single source of truth for managed configuration

- File config holds only process bootstrap settings.
- Import and export bundles are explicit operations; they are never a live second source.
- See ARCHITECTURE §6.

## D-013: Separate `traces.db`

Trace content lives in its own SQLite file, for three reasons:

- it is excluded from ordinary backups by default;
- it can be vacuumed and deleted independently;
- cryptographic erasure works per DEK bucket.

## D-014: Secrets

- **Master key:** a 32-byte KEK loaded from `HP_MASTER_KEY_FILE` (preferred) or `HP_MASTER_KEY`, base64-encoded.
- **Provider secrets** are either:
  - a secret reference (`env:` or `file:`), resolved at runtime and never stored; or
  - an encrypted value: AES-256-GCM with a random DEK per secret. The DEK is wrapped by the KEK and stored with `kek_id`.
- **Rotation:** `harbor-pilot keys rotate` re-wraps the DEKs under a new KEK.
- **API exposure:** API responses only report whether a secret is set, plus a fingerprint hint.

## D-015: Gateway credential format

- **Format:** `hpk_<8-char prefix>_<43-char base64url secret>`, carrying 256 bits of entropy.
- **Storage:** only the prefix and `HMAC-SHA256(pepper, secret)` are stored. The pepper is derived from the KEK with HKDF and the label `harbor-pilot/token-pepper/v1`.
- **Display:** the full token is shown once, at issue time.
- **Scopes:** `gateway:invoke`, `gateway:models`, `usage:read`, `tokens:mint` (child tokens), and `api:*` for service principals.
- **Child tokens:** a principal holding `tokens:mint` can mint short-lived child tokens with bound external refs (used for SpaceMan run tokens).

## D-016: Canonical IR rewritten from scratch

- The IR is typed and carries per-protocol `Extensions`.
- Opaque signed or continuation state is a sealed part. It returns only to the same protocol family and the same upstream lineage. Otherwise it is either dropped, under an explicit `degrade` policy that records the loss, or the request is rejected. It is never converted to text.

## D-017: Failover only before the first byte

- An attempt may fail over only if no byte has reached the client, and only if the failure is classified as not executed: connect error, 401/403/429 before any body, or an explicit provider "not processed" signal.
- An ambiguous execution (a timeout after the request was sent with no response, or a 5xx after the body was sent) is not replayed unless the plan declares the route idempotent-safe. There is no such mechanism by default, so the request stops.

## D-018: Expr for conditions and scores

- **Engine:** `expr-lang/expr` with a typed environment and these limits:
  - `MaxNodes` of 2000;
  - a memory budget;
  - no user-registered functions with side effects;
  - built-ins limited to pure functions.
- **Missing values:** handled with explicit `known()`, `stale()` and `fresh_within()` helpers.
- **Decision tables:** each table declares its hit policy: `first`, `unique` or `collect`.

## D-019: Ledger and reservation model

- The ledger is append-only and idempotent.
- Reservations are taken inside one `BEGIN IMMEDIATE` transaction. The single writer serializes them, so concurrent requests cannot over-allocate.
- A reaper with a lease settles abandoned reservations, including at startup.

## D-020: Hot-path isolation

- Telemetry, the observer and trace capture use bounded channels and drop rather than block.
- Events and notifications go only through the outbox.
- This guarantees that a Pulse, NATS or notification outage cannot stall a stream.

## D-022: UI stack preserved

- **Stack:** React 19.3.1, TanStack Router/Query/Table/Virtual, CSS Modules with `tokens.css`, ECharts 5.6, lucide-react, zod, Vite 7, Vitest and Playwright with axe, all pinned exactly as in Quota Harbor.
- **What changes:** branding only (name, logo, storage key).

## D-023: Auth parameters

**Passwords**

- Argon2id with 64 MiB memory, t=3, p=2, a 16-byte salt and a 32-byte key, stored in PHC format with versioned parameters.
- Passwords are NFKC-normalized and must be 12–1024 bytes.

**Sessions**

- Sessions are stored server-side. The table holds the session-token hash.
- Cookie: `__Host-hp_session`, with `Secure`, `HttpOnly` and `SameSite=Lax`.
- Lifetime: 30 min idle, 12 h absolute.

**CSRF**

- The request's Origin (or `Sec-Fetch-Site`) must be same-origin.
- An `X-CSRF-Token` header must carry an HMAC of the session's CSRF secret.

**OIDC**

- Authorization code flow with PKCE S256, and state and nonce stored server-side.
- ID tokens are signed with ES256, RS256 or EdDSA.
- Users are identified by iss+sub.
- Groups are read from a dotted-path claim (`porch.groups` for Porch).

## D-024: Notifications as a separate consumer

- Notification rules subscribe to domain events read from the outbox stream.
- Each channel adapter has its own delivery table, with the following worker semantics:
  - a lease on each delivery;
  - backoff with jitter, honouring `retry_after`;
  - dead letters after repeated failure;
  - quiet hours and digests.

## D-025: Placeholder format for masking

- **Format:** `HPSEC_<26-char base32>`. It is ASCII-only, needs no JSON escaping, and is unpredictable.
- **Scope:** principal, binding and session.
- **Storage:** memory only, with a TTL (default 2 h) and a cap. Mappings are lost on restart, which is documented.

## D-026: Bridge isolation

**Per account and per request**

- Each account gets its own config directory under `<data>/bridges/<kind>/<account_id>/`, protected by an advisory file lock.
- Each request runs in a fresh working directory, with a scrubbed environment and the binary's built-in tools disabled.
- Client tools are exposed through a per-request loopback MCP endpoint, protected by a one-time token.

**Credential handling**

- The global credential file is never shared or rewritten.
- Bridge isolation must not rely on `--bare`. Per `claude --help` (2.1.318), `--bare` never reads OAuth or keychain credentials, so it cannot work with setup-tokens.
- Isolation therefore comes from `--setting-sources` limited to project, `--strict-mcp-config`, `--tools ""`, a per-request working dir, and a per-account `CLAUDE_CONFIG_DIR`.
- In `-p` mode Claude Code skips settings files that fail validation without reporting it, so the bridge runs a startup self-test (see `docs/contracts/harness-wire-facts.md`).

## D-027: Quota monitors and budgets are managed resources

- A `quota_monitor` resource binds an adapter, its options and write-only credentials, and optionally a provider account. When linked, fresh adapter observations feed that account's routing health: a global bucket at or below `exhausted_below` makes the account unavailable until its reset. Stale or unknown values never decide.
- A `budget` resource limits spend for a scope (global, workspace, project, binding, account) per day, week or month in one currency. Only the cost categories it lists count; by default estimated and actual API charges, never subscription list-equivalent values.
- Budgets are checked inside the reservation transaction, so concurrent requests cannot overshoot together. Threshold events are written to the outbox once per period.
- OAuth tokens from in-app sign-in are sealed with the master key in `quota_oauth_tokens`; the file-based token store of the source project is not carried over.

## D-028: Claude Code bridge conversation model

Verified against `claude` 2.1.318 with a synthetic upstream (see `docs/contracts/harness-wire-facts.md` §1.3):

- Multi-message stream-json input does not reproduce a conversation (each user line is a separate model call and ordering is not preserved). The bridge therefore writes the history as a session transcript and starts the CLI with `--resume`; the final user turn goes to stdin.
- After a client tool call the CLI is parked on its blocked MCP `tools/call` (matched exactly by `_meta["claudecode/toolUseId"]`). The client's tool result answers that call and the same process continues. A plain follow-up turn is written to an idle process's stdin. Processes are matched by account, model, system prompt, tool set and a fingerprint of the conversation.
- When no process holds a tool call (restart, eviction, timeout), the history including the tool result is resumed and the CLI is asked to continue. The CLI inserts its own "No response requested." marker in that case; the attempt records an approximate `tool_continuation` loss.
- CLI retries are disabled (`CLAUDE_CODE_MAX_RETRIES=0`) so upstream errors surface immediately and the gateway's failover policy decides. Compaction, CLAUDE.md loading, auto memory and tool search are disabled; the client owns its context.

## D-029: Trace key partitioning

- One data key per (trace policy, UTC expiry day). It is wrapped by the master key (`trace-key:<bucket>` as associated data) and stored in `trace_keys`; its `expires_at` is the end of that day.
- Each section of a trace is sealed separately with AES-GCM, using `<trace id>|<section>` as associated data.
- Reads check `expires_at` first, so an expired trace is unreadable even before the sweep. The sweep deletes expired traces, their parts and their search entries in batches of 500, then destroys bucket keys with no live trace. Once a key row is gone, any ciphertext left in free pages, the WAL or a backup that did not capture the key row cannot be decrypted.
- The search index (FTS5) only receives text redacted by the trace's redaction policy, even for unredacted traces.

## D-030: Masking precedence and placeholders

- Overlapping detections merge into one span carrying the strongest action. Precedence is block > allow > mask > warn: an allow rule exempts a whole span from mask and warn, never from block.
- Placeholders are `HPSEC_` followed by 20 random base32 characters. They are stable for the same value within one binding and session (or credential when no session is known) and differ across scopes. The mapping is memory-only (24-hour idle expiry, 200,000 entries); after a restart, placeholders the model echoes can no longer be restored.
- Trace redaction is independent: it replaces spans with irreversible `[redacted:<rule>]` markers.
